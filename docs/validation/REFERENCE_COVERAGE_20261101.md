# 参考图覆盖与模型输入诊断

## 范围与冻结

本轮继续 VER-001。目标保持未知猫误确认 ≤5%、已知猫正确确认 ≥80%，同时要求已知猫错误确认、狗图误确认各 ≤5%，不可用数为 0。旧留出集已经查看，本轮仅用它检查模型输入，不用其分数选择方案，也不把它重新当成独立测试。

开发实验的脚本、[协议](recognition-coverage-protocol.json)、[新增参考清单](recognition-coverage-extra-references.json)和[输入诊断](recognition-input-diagnosis.json)在提交 `ebb5985` 冻结后才运行四组比较。四组使用同一组校准查询、同一权重、同一 YOLO 裁剪和同一身份最大相似度聚合，只改变：

| 变量 | 原方案 | 实验方案 |
|---|---|---|
| 模型输入 | 短边缩放至 256，再中心裁剪 224 | 长边缩放至 224，保留比例和完整裁剪主体，居中填充 RGB(124,116,104) |
| 参考数量 | 24 个身份，每个 2 张，共 48 张 | 同 24 个身份，每个 4 张，共 96 张 |

确认参数沿用上轮预先定义的 32 组网格，并同时报告固定 `0.65 / 0.49 / 分差 0.15` 的结果。只在同时满足各项目标的候选中，按正确确认数量、未知/狗误确认数量、已知错误确认数量排序；相同时优先较简单的原方案。若没有优于原方案的候选，就停止本次实验，不追加参数或种子、不消耗新的留出集。

## 已证实的输入问题

诊断脚本调用实际 `detect_and_crop` 和 `preprocess_image`，把模型张量反归一化为可见图片；没有用示意裁剪代替真实输入。输出 35 张“原图 → YOLO 裁剪 → 实际 224 输入”的本机对照图，并记录图像/模型哈希、尺寸和管线版本。以下结论来自实际查看：

- `0404-1` 参考图：YOLO 裁剪尺寸 1467×3484，中心裁剪后几乎只剩胸腹，头脸被裁掉。模型实际接收区域约占 YOLO 裁剪面积的 32.29%。
- `0404-2` 查询：裁剪尺寸 2136×4032，中心裁剪截去耳朵及部分上脸，面积保留约 40.58%。
- `0502-3` 查询：裁剪尺寸 2153×3747，仰头的头脸大部分位于中心窗口之外，面积保留约 44.04%。
- `0502-2`、`0502-4` 查询仍保留面部，但有模糊、低头等情况；两张原参考偏俯视。因此不能把 0502 的三次检索失败全部归因于中心裁剪。
- 35 张诊断图均未读到 EXIF Orientation 标签；这批失败没有证据支持“EXIF 方向错误”解释。本轮不混入未经验证的方向变换。

面积保留率只是几何量，不是身份信息保留率；头脸截断是独立的视觉观察。即使完整保留主体，模型训练分布、个体区分能力和图像质量仍可能限制检索。

## 新参考图的来源与边界

使用相同的 Cat Individual Images v1（Tzu-Yuan Lin / Kaggle `timost1234`，CC BY 4.0）。按固定种子 `2026110103` 对每个已入库身份的未用图片排序，取两张非重复图。准备阶段排除旧校准/留出的所有参考和查询文件、SHA 重复、像素重复及 dHash 距离 ≤4 的图片；再检查新增图片之间的重复候选。

48 张新增图片及原参考伴随图已通过四张联系表逐图检查，没有根据模型分数换图。0171 的新增图包含模糊，0302 戴帽，0395 有遮挡，均保留并记录；来源身份标签未因外观或得分修改。多数新增图片仍与原图同姿态、同背景，**参考数量翻倍不等于补齐跨角度、跨时段覆盖**。

照片不提交至 Git，也不作为 CI 结果上传。清单保存来源、许可、内容哈希、视觉审查和联系表哈希。狗图继续沿用原校准集的 AFHQ 研究负例及 CC BY-NC 4.0 限制。

## 验证方式

四组真实开发对照已完成，见[完整结果](recognition-coverage-comparison.json)。原方案的 116 张查询前五名身份全部复现，分数最大差 `1.37×10^-6`，通过预设 `2×10^-5` 容差。

| 固定 0.65 / 0.49 / 分差 0.15 | 已知正确确认 | 未知误确认 | 狗误确认 |
|---|---|---|---|
| 中心裁剪，2 张参考 | 33/36 | 3/60 | 0/20 |
| 中心裁剪，4 张参考 | 34/36 | 4/60 | 0/20 |
| 完整主体填充，2 张参考 | 32/36 | 3/60 | 0/20 |
| 完整主体填充，4 张参考 | 34/36 | 2/60 | 0/20 |

四组已知猫 Top-1 均为 36/36，已知错误确认均为 0。不能从这组数据宣称修复了旧留出身份 0502 的检索错误，因为它不是本轮校准查询身份。增加参考数量单独使用时提高了未知猫误确认；只改输入几何也没有提高确认覆盖。

按冻结网格分别选择策略后，四组最优可行候选的已知正确确认 / 未知误确认分别为 `33/36、3/60`、`32/36、2/60`、`33/36、3/60`、`35/36、3/60`。最后一组选中 `0.57 / 0.49 / 分差 0.15`，因此获得继续开展新实验的资格；该开发参数不会直接作为业务默认。

代码增加 `RECOGNIZE_PREPROCESS=letterbox224` 实验选项，并将精确变换版本写入参考库清单。默认仍为 `center224`。切换模式后拒绝旧参考向量，必须重新构建；切回原模式也重新校验兼容性。真实 Torch 对三种图片尺寸、两种模式共六组张量逐元素检查，与冻结公式完全一致。

本机实验使用独立 CPU Docker 镜像 `cat-coverage-study:20261101`，禁网，2 CPU / 8 GiB；模型和数据只读。模型 SHA 为 `32f04b89…e6a1b4beb6e`，检测器为 `5d4a90cd…fe4fe5`，完整值见协议。参考数量实验在内存中建索引，不连接业务数据库、不发布业务向量。

比较脚本先复算原校准基线：要求每张查询前五名身份完全一致，分数最大差不超过 `2e-5`，否则拒绝输出有效比较。模型特征必须维度正确、有限且归一化。新实验脚本只接受已冻结的校准清单，拒绝留出查询、未审查额外参考、身份错配、重复样本和哈希变更。

这是一轮开发对照，未经过完整的参考库构建/发布/API 识别链路，不能代替应用验收。只有出现更优候选后，才实施可追踪的生产管线版本，在新的校准身份上冻结策略，并使用新的留出身份验收。旧向量不能与新预处理混用。

## 新身份上的校准与验收协议

开发对照选出候选后，另按固定种子 `2026110104` 建立[新协议](recognition-coverage-validation-protocol.json)。新图库为 24 个身份、96 张参考图，校准/留出各有 12 个已知身份的 36 张查询、20 个未知身份的 60 张查询及 20 张狗图。共 328 张唯一图片，两组查询身份无交叉，见[边界检查](recognition-coverage-boundaries.json)。[历史暴露清单](recognition-coverage-prior-exposure.json)和额外排除名单涵盖前期已用、已下载和已审查的身份；旧实验分数没有参与新参数选择。

新数据在推理前经历数轮标签审查，全部使用同一个种子、样本数和预先定义的资格条件。0052 在固定去重后不足 7 张，另有 18 个身份因多猫/疑似多猫或身份混杂被整组排除；没有根据识别结果删图或改标签。0437 混有虎斑和黑白猫；0323 疑似混入不同橘猫。模糊、遮挡、异常姿态、旋转画面和同背景照片在身份分配无歧义时保留。[视觉审查记录](recognition-coverage-visual-review.json)保存各次分配、排除理由和实际查看的联系表哈希；`fresh-v1` 至 `fresh-v5` 是推理前的数据整理版本，不是五次质量测试。

第二轮补位重放曾将已接受的 0305 在同一“校准/已知猫”组内移位，照片与角色未改变。准备工具因此增加 `--previous-plan`，后续替补严格保留已接受槽位；已用实际前后分配验证非排除位置未变化。

最终[校准清单](recognition-coverage-calibration-manifest.json)和[留出清单](recognition-coverage-holdout-manifest.json)在 `eefed5e` 提交并推送后才开始新校准推理。新校准仍只搜索原定 32 组确认策略；无可行策略就停止，不打开留出。若有可行策略，另提交冻结选择后才运行一次留出。生产默认值暂不替换。

首次本机完整校准在 Windows bind mount 上反复读取权重较慢，于参考构建 42/96 张、尚无查询结果时中止。随后把同一冻结输入复制到项目专用容器卷，模型/数据只读挂载、禁网及 2 CPU / 8 GiB 限制不变，再从新目录构建；见[运行转换记录](recognition-coverage-runtime-transition.json)。这不是质量失败后的换数据重试，未修改通过线、模型或任何样本。此处运行时间也不用于宣称预处理改善了线上延迟。

新校准完整执行 116 张查询，96 张参考图真实构建并发布，输入错误与 unavailable 均为 0。见[推理结果](recognition-coverage-calibration-result.json)、[构建记录](recognition-coverage-calibration-build.json)和[日志](recognition-coverage-calibration-inference.log)。按冻结顺序选出 `confirmed=0.70 / uncertain=0.49 / minimum_margin=0`，已知正确确认 36/36、已知错误确认 0/36、未知误确认 3/60、狗图误确认 0/20。原 0.57 / 0.49 / 分差 0 在相同新校准排名上将 18/60 未知猫误确认，输入变换本身没有解决确认规则问题。

[新冻结策略](recognition-coverage-selected-policy.json)包含完整 32 组结果、模型/管线、图库、两组清单、校准结果及策略代码哈希。该选择单独提交后才允许执行新留出；开发对照里选出的 0.57 / 0.49 / 分差 0.15 没有直接沿用到新身份。

## 可复跑入口

- `scripts/prepare_reference_coverage.py`：按固定顺序增加参考候选，产生待视觉审查清单。
- `cat-backend/scripts/inspect_recognition_inputs.py`：按指定身份输出真实输入对照图，不计算识别排名。
- `cat-backend/scripts/compare_reference_coverage.py`：读取校准清单、额外参考清单、冻结协议及原基线结果，输出四组完整排名和 128 组策略结果。

准备和比较均要求新的输出目录，不覆盖已冻结证据；照片与本机中间产物保留在忽略的 `artifacts/coverage/`。原校准/留出结论见[上轮记录](RECOGNITION_CALIBRATION_20261101.md)。

[手动校准工作流](../../.github/workflows/recognition-calibration.yml)新增 `study=coverage`，原实验使用 `study=original`。两者仍分为 `phase=calibration` 和 `phase=holdout`，后者要求已有单独提交的成功校准选择。新模式通过 `RECOGNIZE_PREPROCESS=letterbox224` 注入 API 与参考构建 worker；实际业务启用前需校验数据适用性并重建参考库，不能复用原向量。
