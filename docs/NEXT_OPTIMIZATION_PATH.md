## A：先让下一次修改有可靠落点

1. **检查现有未提交改动及依赖关系。** 按认证/审核、数据时间与归属、客户端合同、运维、测试文档划分可评审单元。数据模型、迁移和依赖它们的代码保持兼容；不为了拆小而制造无法启动的中间版本。保留现有验收记录和文件指纹作为历史证据。
2. **验证干净检出。** 使用新的临时检出目录执行 `npm ci`、Python 依赖安装、Alembic 空库升级和两端构建。当前 `.gitattributes` 把 PNG/JPG 等放入 LFS，而 Web/小程序 CI 的 checkout 未设置 `lfs: true`；先复现实际产物，再修正检出或资源管理方式。增加图片解码/文件签名检查，不能只判断文件存在。小图标是否退出 LFS可后续单独处理。
3. **让浏览器测试可在 CI 使用。** 改造当前 Edge 本地脚本，支持 CI 提供的 Chromium、可配置端口和自动失败产物。继续使用独立数据库，覆盖管理登录、普通登录、图鉴、过期凭据和请求失败；把“保存→待审→审核→公开列表/地图数据”的跨角色链路加入验收。
4. **收紧启动行为。** 逐步移除应用导入时 `create_all`，由显式迁移管理结构；缺少迁移时启动给出可诊断错误。测试夹具继续自行建库。复验空库、支持的旧库、重复升级和失败后的恢复路径。

这一阶段主要收口 ISS-030 和 ISS-031，防止本机缓存、未拉取资源或隐式建库掩盖交付问题。

## B：把 ISS-028 拆成四次可验收的修改

B 阶段规划时，`ai.py` 缓存旧索引和猫名映射，旧构建工具顺序写文件，档案更新、失败和换库之间缺少共同版本依据。下列 B1—B3 已按最小架构完成本地验收，先支持可追踪的全量重建，实际耗时证明有必要后再增加增量索引。

### B1：身份与版本校验

- 为数据库/参考目录引入持久身份标识；猫使用不可变参考身份，保留现有数字 ID 的 API 兼容性。迁移生成标识一次，重建时不得重新分配。
- 清单至少包含：参考库版本、目录修订号、模型 SHA256、预处理/裁剪版本、向量维度、猫身份映射、源图哈希、各产物哈希和构建时间。
- 名称更改不改变猫身份。旧参考库缺少清单时进入“待校验/待重建”，不得根据同名或碰巧相同的数字 ID 自动认定兼容。
- 模型、映射或产物校验失败时返回 `unavailable` 并给管理员可诊断原因；不要误报成“未知猫”。

验收：构造两个数字 ID 相同但猫不同的数据库，必须拒绝跨库匹配；模型/维度/哈希不一致、损坏清单均失败；兼容快照可加载。这些控制流测试可使用合成向量，不能据此宣称真实识别准确。

### B2：可追踪重建

- 猫身份/参考照片变更在同一数据库事务内更新目录修订号；记录需要重建的状态。审核通过和成功入参考库是两个可见状态。
- 先提供管理员触发的单写入者重建命令，记录任务 ID、输入修订号、成功/失败原因。接口仅触发任务，不在上传/审核请求内执行长时间推理。
- 从固定输入快照构建到独立版本目录；检查空向量、非有限数、维度、归一化、身份映射、照片可读性和样本数量。发布前确认目录/模型没有在构建期间变化。
- 必需参考图失败时默认阻止发布并列出问题，避免悄悄漏掉某只猫；确需排除的参考图由管理员显式调整后重建。

验收：新增照片、新猫、删除照片、改名和构建期间继续修改均有明确结果；失败构建不能覆盖当前产物；两个重建请求不会互相写坏文件。

### B3：发布、刷新与回滚

- JSON、向量和清单放入同一不可变版本目录，通过原子更新“当前版本指针”发布，读者只能看到完整版本。
- 每个 worker 在处理识别前检查版本/目录修订，按需加载并校验新快照；以短锁切换内存引用。Redis 通知用于加速，可靠性不能只依赖易丢失的 Pub/Sub。
- 无兼容版本时停止自动识别；旧版仅在与当前模型及有效档案仍兼容时继续服务。删除猫或错误映射不能等到方便时再失效。
- 回滚必须重新校验当前数据库兼容性；旧目录存在不等于可以直接恢复为有效版本。

验收：至少两个真实后端进程执行更新和检索，已失效映射不会继续被使用；中途终止构建、损坏候选产物、Redis 通知丢失和重启均可恢复；回滚拒绝不兼容的旧版本。

### B4：管理可见性

- 展示当前版本、参考图数量、目录是否有未发布变化、任务进度和最近失败原因。
- “猫档案已创建”与“识别参考已更新”分别显示；失败可重试，不能在尚未生成向量时宣称已经可识别。
- 只有通过全部本地控制流和多进程验收后关闭 ISS-028；真实模型效果继续由 VER-001 单独验收。

## D：让合同变化更早暴露

优先处理认证、分页、识别四态和审核四个边界。为 FastAPI 响应补明确 schema，从 OpenAPI 生成可复用 TypeScript 类型或经过校验的共享合同；Web fetch 与 Taro upload/request 保留各自传输实现，共享业务字段和错误语义。

类型化客户端使用 `unknown` 接收未验证 JSON，经必要的运行时检查后返回业务类型；不把 `request<T>` 强制断言当成服务端数据已验证。新增和迁移的边界不得再引入 any。

以独立 strict 配置或包边界逐步扩大检查范围，先客户端与状态转换，再相关页面。Taro 第三方声明问题单独跟踪；验证兼容版本前保留有说明的 skipLibCheck，应用源码检查继续生效。

后端按“奖励结算 → 审核与通知 → 个人统计 → 参考库服务”顺序拆分。路由负责输入与权限，服务负责事务和业务，数据访问负责查询；明确由谁提交事务，避免嵌套 helper 私自 commit。每次只迁移一个职责，并比较状态、事件、XP、权限与错误响应。

告警按类别治理：先处理 Hook 依赖和副作用问题，再处理 unused/类型问题，最后按文件清理格式。新增代码不增加遗留告警；降低警告阈值应随实际修复进行，不通过关闭规则实现。测试数量增长不是本阶段的验收目标。

## E：按测量结果做性能与产品优化

1. **先确定内测规模。** 记录目标硬件、预计数据量、同时在线数、主要读写比例，以及普通 API 和识别各自的 p95 延迟/错误率预算。这些是待确认的产品指标，当前不虚设“已达标”的数值。
2. **建立可复跑数据集与压测脚本。** 覆盖图库、排行榜、通知和识别，报告查询数、耗时、RSS/模型内存、SQLite 等待与错误；同时测冷启动和稳定运行。
3. **优先验证三个源码候选瓶颈。** 图库目前全量读取后在 Python 排序分页，优先尝试数据库合并查询和分页；排行榜检查逐用户聚合；通知检查逐条提交。只有前后对照证明收益且行为不变才保留优化。
4. **前端按真实加载成本拆包。** 当前主 JS 约 502.63 kB，只说明触发打包警告。先测移动网络的加载、解析和主要交互耗时，再决定大依赖延迟加载或拆分；视觉美化不优先于失败可恢复和弱网可用。
5. **数据规模证明确有需要后再选数据库/检索升级。** SQLite、IndexFlatIP 的保留或替换应由写入竞争、数据量和部署需求决定。
6. **内测前核对产品承诺。** 路线热度推荐、按站名打卡仍是轻量玩法，不等于路网最优或可信到访。新猫合并和发现者勋章若不是内测必需，继续明确标为未实现。完成 ISS-031 与 VER-007 的文档/许可核对。
